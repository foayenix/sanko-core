# Practitioner-reviewed evaluation set

```bash
npm run review:status                       # where the set stands against the gate
npm run review:packets                      # something a practitioner can read
npm run review:packets -- --language yo     # one language at a time
npm run review:apply -- --file evals/review/decisions.json
```

`review:packets` writes one plain-text packet per unreviewed case — what the
practitioner said, what Sanko is expected to record, and the four rubric
questions — plus a combined file for printing and a pre-filled decisions file.
`review:apply` writes the approvals back into the case files. It refuses a
`reviewer_ref` that is a name, a phone number or a database id, and it never
writes anything for a rejected case: a rejection means the case needs fixing or
removing, and a review block on it would make it look checked.

Nothing in this repository can approve a case. `apply` only records a decision a
person already made.


`npm run eval:reviewed` runs the real agent loop only on practitioner-approved cases and
fails before making model calls unless at least 100 are eligible. The current eight cases
are exploratory and do not count toward that threshold.

## What counts as reviewed

A practitioner should review the source wording and expected outcome together. Approval
means the case preserves what they intended, does not add medical or botanical claims they
did not make, and expects the correct Vault action. An admin-only review, a correction row,
or a synthetic paraphrase is not practitioner review.

Add this block only after approval:

```json
"review": {
  "status": "approved",
  "reviewer_role": "practitioner",
  "reviewer_ref": "PR-7F2A",
  "reviewed_at": "2026-08-13T14:30:00Z",
  "rubric_version": "practitioner-v1"
}
```

`reviewer_ref` must be a stable pseudonym, never a name, phone number, patient identifier,
or database UUID. Keep the identity-to-pseudonym mapping outside the repository. Source
messages must be de-identified before becoming fixtures.

## Review rubric

The practitioner confirms all of the following:

1. The case wording faithfully represents a real interaction or an approved de-identified
   rendering of one.
2. Every expected plant, preparation, dosage, condition, and action reflects their intended
   meaning; omitted information remains omitted.
3. The case contains no patient-identifying information.
4. The case is approved for model evaluation and is not included in training or prompt
   development data.

### Editorial fixtures awaiting practitioner review

Cases 09–50 have a separate `editorial_review` block. It records that their structure,
tool expectations, de-identification, and labels received an editorial consistency pass,
while explicitly keeping `practitioner_review` set to `pending`. They are useful for
engineering regression runs but do not count toward `npm run eval:reviewed` and must not
be described as practitioner-approved evidence.

They are reproducibly generated by `node scripts/build-editorial-eval-fixtures.js`.
After a practitioner reviews one, remove `editorial_review` and add the practitioner
`review` block above with the real approval timestamp and a stable pseudonymous reviewer
reference.

Use multiple practitioners and track coverage across language, message medium, unknown
plants, partial records, corrections, browsing, and consent-gated patient workflows. Do not
create many superficial paraphrases of one interaction: they are correlated, not independent
evidence.

## Cases drafted from production failures

`npm run eval:draft` turns corrections into candidate cases in
`evals/cases/drafts/`. They are **not** reviewed cases and the runner does not
read that directory. Each one carries a `draft_origin` block instead of a
`review` block, recording which correction it came from, which model made the
mistake, and what still has to happen:

1. de-identify the wording in `turns` — it is verbatim practitioner speech, which
   is why the directory is gitignored;
2. confirm with a practitioner that `expect` is what they meant;
3. replace `draft_origin` with the `review` block above and move the file into
   `evals/cases/`.

Drafting holds the correction out of the training export (011). That separation is
the point: a case the model was trained on measures memory, not capability. If you
discard a draft, `node scripts/draft-eval-cases.js release` returns the correction
to training rather than retiring it silently.

Drafts are correlated with production traffic, so they are not a substitute for
deliberately chosen coverage — a hundred cases drafted from one busy practitioner
is still one practitioner. Use them to find gaps, not to fill the quota.

## Case format

Copy [`templates/practitioner-reviewed-case.json`](templates/practitioner-reviewed-case.json),
replace every placeholder, and place the completed case in `evals/cases/`. `input` is for a
single turn; `turns` is for a conversation. The runner rejects malformed or partial review
metadata and duplicate case IDs.

### Button expectations

`expect.choices` asserts how a question was *asked*, not what was recorded:

- `"required"` — some reply in the run offered quick-reply buttons. A floor rather
  than an assertion about one message, because which turn carries a confirmation
  depends on how the model paces the conversation.
- `"forbidden"` — no reply did. This is the strict direction: a list of plants to
  tap puts names into the archive that the practitioner never said.

`expect.choices_include` additionally names options that must appear, matched as
case-insensitive substrings (`["worse"]` is satisfied by a `Worse` button).

Every case is also checked for a leaked sentinel — a literal `[[…]]` surviving
into a message — whether or not it declares a button expectation. `splitChoices`
only reads the last line, so a sentinel written anywhere else reaches the
practitioner verbatim, and that is a bug in every case.

Run the preflight gate without waiting for model output:

```bash
npm run eval:reviewed
```

Until 100 approved cases exist, the command exits with the exact eligible count. Once the
gate passes, the result JSON records the reviewed-case count, minimum threshold, and rubric
versions used. Keep the resulting case set frozen when comparing models.
